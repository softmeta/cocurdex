# Cocurdex

## Working principles

- Use English for code, documentation, and commit messages.
- macOS, Windows, and Linux are equally supported release platforms. Design, implement, and verify every change for all three; see [Cross-platform](#cross-platform).
- Do not tailor answers to please the user. Reason from first principles and the underlying problem, and propose the most sound solution even when it differs from the user's suggestion; say plainly where and why you disagree.
- Treat reference implementations — open-source projects, competitors, big-vendor products — as evidence, not templates. Before adopting a design, data model, or library, state the problem it must solve in this product (agents and people as equal users, every client, all three platforms, persisted data that outlives releases) and choose what solves that best; copy a reference's decision only when it holds up on those terms, and record where and why you deviate.
- Fix root causes in the design, data model, API, or control flow, and remove obsolete internal paths. Released contracts — persisted data, settings, and the `cocurdex` CLI commands, flags, and output that scripts and product skills depend on — change only additively or with a migration. Add other compatibility layers only when explicitly requested.
- Every client — the Electron desktop app, the web client, and the planned mobile app — must keep functional correctness, user experience, performance, and memory use at the same bar. Do not trade one for another: a change that works but buffers whole files, duplicates large payloads across processes, blocks a shared connection, or regresses first paint is not done. Move large or binary data by streaming with on-demand reads (for example HTTP `Range`), not as base64 or whole-file RPC payloads, and measure size, latency, and peak memory on realistic inputs before and after.
- Work autonomously. Do everything you can run or verify yourself — builds, dev app restarts, daemon rebuilds, CDP attaches, CLI calls, PR checks — instead of asking the user to do it or waiting for them. Ask only for decisions that belong to the user or for actions you cannot perform, such as credentials, interactive logins, or physical devices.
- Ask the user for every decision that is theirs through the agent's structured question tool (for example `AskUserQuestion`), with concrete options and your recommendation first, instead of burying the question in a prose reply. Keep working on everything that does not depend on the answer.
- Do not idle while long work runs. Start builds, e2e runs, CI, and other slow checks in the background, then keep working on independent tasks in parallel (the next issue, a review thread, a design board, investigation for follow-up work) and return to the results when they finish. Run independent checks, such as the iOS and Android flows, concurrently rather than one after another.
- Write only code and tests. Do not write documentation in any form: no READMEs, design docs, ADRs, glossaries, guides, code comments (`//`, block comments, JSX comments), or JSDoc. Express intent through naming, types, structure, and tests. Tool-required directives and agent instruction files (`AGENTS.md`, skills) are the only exceptions.
- Prefer the latest stable dependencies. Use prerelease or deprecated versions only when explicitly requested or required for compatibility. Before adding or upgrading a dependency, read its current release from the registry (`npm view <package> version dist-tags`); do not take versions from memory, templates, scaffolders, or reference projects. When a platform pins a dependency set (an Expo SDK pins `react-native` and `react`), use the latest stable release of the platform and the versions it pins. Latest means the newest release that passes pnpm's minimum release age: widen the range so pnpm can pick it, and never add `minimumReleaseAgeExclude` entries, which pnpm and scaffolders may write on their own; revert them.
- Verify current information, versions, API behavior, platform limits, troubleshooting, configuration, and third-party tooling against official documentation, repositories, release notes, or standards before drawing conclusions or changing code. Prefer current official sources when sources conflict and explain the choice. If verification is unavailable, state the uncertainty and limit conclusions to local evidence. Verify advice with cost, risk, or long-term maintenance implications.

## Cross-platform

Assume nothing POSIX-only. When a change touches processes, shells, signals, paths, file permissions, line endings, or packaging, handle each platform explicitly.

- Spawn third-party executables through `spawnCommand` from `@cocurdex/agent-adapters` (cross-spawn). A plain `spawn`/`execFile` cannot launch Windows `.cmd`/`.bat` shims such as `npx` or npm-installed CLIs, and does not apply `PATHEXT`. Pass arguments as an array; never build a shell string.
- Stop process trees, not single processes. Windows has no signals: `child.kill()` is an immediate `TerminateProcess` that orphans grandchildren, so use `taskkill /T /F` (see `killProcessTree`). On POSIX, escalate from a graceful stop to SIGTERM to a tree kill.
- Build paths with `node:path`, compare them with platform-aware helpers (Windows and default macOS volumes are case-insensitive), and never hardcode `/`, `~`, `HOME`, or `/tmp`; use `os.homedir()`, `os.tmpdir()`, and the app's user-data path.
- Do not depend on tools a platform may lack (`which`, `ps`, `unzip`, `bash`, GNU flags) without a fallback for the others. Write files with explicit encodings and tolerate `\r\n` when parsing tool output.
- Verify on the platforms you can run and state which ones were not verified. Prefer pure functions that take `platform` as a parameter so Windows and Linux branches are covered by unit tests on any host.

## Git and branches

Never change code or commit on `main`. Create a branch before the first edit or commit. If work has already landed on `main`, move it to a branch with `git branch <name>`, `git checkout <name>`, then `git branch -f main <original-commit>`, leaving the working tree untouched. Never push to `main` or rewrite its history.

When the checkout is already on a branch other than `main`, reuse that branch instead of creating or switching to a new one. Switching branches interrupts other tasks sharing the checkout, and a shared worktree cannot check out the same branch twice. Only create or switch branches when explicitly asked.

Do not open a new branch unless it is necessary. Every extra PR is one more round of checks, bot reviews, and merges for the user to track, so keep one open PR per line of work. Unrelated follow-up fixes found while working go on the current branch and its PR; do not split them into separate branches or propose doing so. A new branch is necessary only when starting from `main`, or when the current branch's PR has already merged. Even then, first look for an open PR you or another agent already have in progress (`gh pr list --state open --author @me`) and push to that branch instead of opening another PR beside it.

Land changes through a branch and a pull request: push, open the PR, watch its checks and review threads, then queue it with `gh pr merge <n>`: `main` requires a merge queue, which tests the PR on top of the latest `main` and merges it with a merge commit once the required checks pass, so never merge `main` into a branch only to bring it up to date. Clear every review thread first — fix it, or reply with a reason and then resolve it. Docs, skills, and tooling changes take this path with no version bump and no tag; only an explicit release request bumps `apps/desktop/package.json` and pushes a `v<version>` tag. See `.agents/skills/desktop-release`.

Review bots (Cursor Bugbot, the Cursor security review) comment on new commits, so every push invites another round. Converge instead of looping:

- Read every open thread, handle them all, then push once. Do not push per thread.
- Change code only for a finding you can state as a concrete trigger and a wrong, observable result, and add the test or scenario assertion that fails on it first. Answer false positives, style notes, and speculative risks with the reason and resolve them without a code change.
- When a round brings only findings of that second kind, stop iterating: resolve them and merge once checks pass.
- Record a fact that keeps causing false positives in `.cursor/BUGBOT.md`, and turn a class of real findings that recurs into a lint rule, type, or test.

When a push starts no checks, read `gh pr view --json mergeStateStatus`: GitHub runs no `pull_request` workflow while the PR conflicts with its base (`DIRTY`). Merge `main` into the branch, resolve the conflicts, and push; do not rebase or force-push a shared branch.

Address GitHub objects (review threads, comments, runs, check suites) only by IDs a query returned in this task. A guessed or remembered node ID can name an object in another repository, and a write through it posts there; after any write, confirm the response names this repository.

CI fingerprints the tree without `AGENTS.md`, `CLAUDE.md`, root `*.md`, `docs/`, Markdown under `.agents/`, `.claude/`, and `.cursor/`, and the desktop `version` field. Once the required jobs (workspace and desktop) pass, it records that fingerprint, and the mobile jobs record their own; a later run with the same fingerprint anywhere in the repository (the same PR, the merge queue, or `main`) skips the jobs it covers. Android mobile e2e is required on pull requests through the `Mobile` check, which passes only when every Android mobile job passed or was skipped as unaffected; iOS runs beside it and reports, but its failures do not block, since free macOS runners are too slow for a required check; the merge queue skips the mobile jobs, since a PR cannot be queued before they pass, and `main` runs both appearance and locale runs on each platform after the merge. A docs-only or version-only push therefore costs one short job; anything else the tests could read must stay out of that exclusion list.

## Architecture: daemon, host, and clients

Reusable product capabilities belong in `packages/daemon`, exposed through `@cocurdex/rpc`. Ask: would a browser client need this capability through the daemon? If yes, use daemon RPC; desktop-only host APIs use Electron IPC.

| Layer | Responsibilities |
| --- | --- |
| Daemon | Sessions, worktrees, notes, issues, workflows, providers, agent roles, product settings, permissions, plan approvals, headless workspace Git/filesystem operations, and all persistence. SQLite is owned exclusively by the daemon. |
| Shared contracts | Types and invariants in `@cocurdex/shared`; named product RPC methods in `@cocurdex/rpc`. Do not add product behavior to `storage.call`. |
| Electron host (`apps/desktop/electron`) | Windows, menus, native dialogs, system appearance/fonts, protocols, BrowserView, PTY, file watching that requires `BrowserWindow`, updates, and thin daemon forwarding. Forwarding handlers only validate and call `requestDaemon(...)`. |
| Clients (renderer, CLI, future web/mobile) | UI and navigation orchestration; read and write product state through daemon contracts. No duplicate business protocols or client-owned product policies. |

Capabilities needed by the CLI must not exist only in IPC. When modifying IPC that contains product logic, move that logic into the daemon instead of extending it there.

The daemon serves remote principals (paired devices, the web client) as well as the local user. Every RPC that takes a filesystem path, for reading, writing, importing, or exporting, checks the caller's principal before touching disk: a non-local principal may only reach paths whose real path lies inside a registered workspace, and a write checks its existing parent directory. Enforce it in the daemon handler, not in a client, and cover it with a test that a device principal is refused outside every workspace and leaves nothing behind.

Right-panel features (files, Git, notes, issues, decks, browser, PDF, terminal) are agent-native, not human tools with agent access bolted on. Whatever a person can create, change, or read in such a view, an agent can do through the `cocurdex` CLI and a product skill, backed by the same daemon capability; design that capability and its CLI together with the UI, and do not ship UI-only actions. Agent output lands as ordinary product data that the person sees, edits, and undoes in the same view, and an agent can read back the structured state it needs to check its own work. When a host limitation keeps a feature from meeting this bar, say so in the PR.

## Data compatibility

Persisted user data outlives any single release. Never delete, recreate, or rewrite a database because the application version changed.

- Migrate `cocurdex.sqlite` forward in `packages/db/src/migrations.ts`. Every schema change bumps `CURRENT_SCHEMA_VERSION` and adds a step to `MIGRATION_STEPS` that preserves existing rows.
- Keep migrations additive or value-preserving. Add and backfill columns instead of renaming or dropping columns that hold user data; a rename copies the old values into the new column before the old one is removed.
- Treat persisted JSON columns (`provider_snapshot_json`, `attachments_json`, `origin_json`, workflow artifacts) as versioned data: read old shapes, and change them additively or migrate the stored values in the same release.
- Keep `getDefaultUserDataPath()` and `DATABASE_FILENAME` stable. A new channel, build flavor, or rename must not move where an installed app reads its existing data.
- Recreate only a file without the `COCU` application marker, and move it aside as a `.bak-<timestamp>` file first. Refuse a database written by a newer schema version; never downgrade or delete it.
- Opening a database that needs a migration writes a `cocurdex.sqlite.pre-migration-<timestamp>` snapshot. The newest snapshot is always kept; older ones are deleted once they are 14 days old, and at most three are kept.
- Cover each migration with a test that seeds the previous schema, migrates, and asserts that sessions, workspaces, messages, notes, and issues survive.

## Verification and tests

After edits, run applicable checks in this order and fix reported issues:

1. For new `t("...")` calls, run `pnpm --filter @cocurdex/<desktop|mobile> i18n:extract`, complete en-US and zh-CN translations, then run `pnpm --filter @cocurdex/<desktop|mobile> i18n:types` and `pnpm exec biome check --write apps/<desktop|mobile>/src/i18n` (biome normalizes the generated `.d.ts`; CI fails on stale output). `src/locales/*.json` and `src/i18n/*.generated.d.ts` are generated artifacts: resolve merge conflicts by rerunning this chain, never by hand-editing them.
2. When a change touches `theme-preset.css` or `theme-tokens.css`, run `pnpm --filter @cocurdex/mobile generate:theme-colors`; mobile colors are generated from them and CI fails on stale output.
3. Run the affected packages' TypeScript checks, scoped to changed TypeScript source files.
4. Run `pnpm exec biome check --write <changed-files>` for supported files. For Markdown-only changes, run `git diff --check`; no TypeScript check is needed.

Use TDD for critical pure functions and similarly stable logic. UI, feature flows, and rapidly changing behavior do not require TDD; add valuable regression coverage when behavior stabilizes.

- Test important business semantics, algorithms, state transitions, protocol/persistence boundaries, and high-risk regressions, not coverage numbers.
- Avoid testing implementation details such as classes, DOM nesting, indexes, internal call order, trivial string assembly, or pass-through getters unless they express an explicit visual, accessibility, or protocol contract.
- Import tested modules directly and mock real boundaries, not broad barrels or large objects. Avoid unrelated module initialization; do not export internals solely for tests.
- Do not write tests that grep source text for the presence or absence of strings, imports, or constructs (logging lines, `useEffect`, file layout), or that assert on incidental implementation text. These tests break on harmless refactors while protecting no observable behavior; enforce the intent with a lint rule, review, or a behavior-level test instead.
- Rewrite or remove brittle tests that break during routine refactoring or UI/copy changes without protecting important behavior. Do not distort production code to preserve them.
- Do not add low-value tests. Every committed test costs CI time and maintenance, so add one only when it guards behavior that is important, likely to regress, and not already covered; a one-off layout or styling bug in a single view, especially one fixed in a shared component, does not qualify. Verify such a fix with a throwaway check (a temporary scenario or a CDP measurement run before and after) and discard it instead of committing it.

Tests are a maintained asset and live in the root `tests/` folder, never next to source: `tests/unit/<package>/` for unit and integration tests, `tests/e2e/` for process-level e2e, `tests/scenarios/` for app-level e2e, and `tests/harness/` (`@cocurdex/test-harness`) for what e2e, scenarios, and mobile e2e share: the daemon process helpers, the LLM stub, and the fixture database. Keep e2e-only helpers in `tests/e2e/helpers`, so an e2e test edit does not rerun the UI scenarios. Each `tests/unit/<package>` is its own workspace package, `@cocurdex/unit-<package>`, with its own `vitest.config.ts` (`pnpm --filter @cocurdex/unit-daemon test`). Tests import the code under test through package public entries, test-only subentries such as `@cocurdex/daemon/testing`, or the `@cocurdex/<package>/internal/<path>` subentry for modules a public entry does not export; desktop tests use `@/` for `apps/desktop/src` and `@desktop/` for the rest of `apps/desktop`. Never import through `packages/*/src` or relative paths into source folders, and resolve source files at runtime with `createRequire(import.meta.url).resolve(...)` instead of `import.meta.url`-relative paths. Production code must not import `internal` subentries; biome enforces this. Keep fixtures fixed and committed under the owning test folder (for example `tests/scenarios/fixtures/`), generated deterministically where possible, so every run sees the same input. Tests leave nothing behind: create temporary directories with `createTempDirs()` from `@cocurdex/test-fixtures/temp-dirs` and call its `cleanup()` in `afterAll`, and never write directly into `os.tmpdir()`.

CI runs every check through Turborepo (`turbo.json`) with `--affected` at task level (`futureFlags.affectedUsingTaskInputs`): on a pull request or in the merge queue, a task runs only when its own `inputs` or a workspace dependency changed since the base, and the `changes` job starts each desktop runner only when `turbo run ... --affected --dry=json` selects one of its tasks. Desktop-build-backed tasks (`@cocurdex/e2e#test:desktop`, `@cocurdex/scenarios#test:ui`, `@cocurdex/desktop#check:startup-bundle`) depend on `@cocurdex/desktop#build`, so run them through `pnpm exec turbo run <task>` to build first; give such a task narrow `inputs` so an unrelated test edit does not rebuild the app, and depend on `^transit`, not `transit`: the package's own `transit` hashes every file in it, while `^transit` brings in only its workspace dependencies. After changing `turbo.json` or a test package's dependencies, append a blank line to a file the task should and should not see and confirm with `TURBO_SCM_BASE=HEAD pnpm exec turbo run <task> --affected --dry=json`. A change under `.github/`, to the root manifest, `turbo.json`, or the lockfile runs everything, and so does every push to `main`. Turbo sees only files inside a package and its declared `workspace:*` dependencies, so a package whose tests or scripts read, spawn, or build another workspace package (for example `tests/e2e` running `apps/cli`, or `tests/mobile` building `apps/mobile`) must list it as a dependency; otherwise its cached result goes stale and CI skips it when that package changes. Mobile e2e reuses a native build cached by `@expo/fingerprint` and swaps in the current JavaScript with `@expo/repack-app` (`pnpm --filter @cocurdex/mobile-e2e app -- fingerprint|build|repack`); a native change outside what the fingerprint sees, such as a new build flag, belongs in `tests/mobile/app.ts`'s build inputs.

`tests/e2e` (`pnpm --filter @cocurdex/e2e test`) runs deterministic process-level e2e: it spawns the real daemon binary and CLI against an isolated `COCURDEX_USER_DATA_PATH`, then drives production clients over the real socket. Tests that need build output live in `tests/e2e/desktop/`: `smoke.test.ts` launches the built Electron app and verifies the window, the spawned daemon, and a clean renderer, and `bundled-daemon.test.ts` drives the bundled `daemon.cjs`; they run only through `pnpm exec turbo run test:desktop --filter @cocurdex/e2e`, which builds the app first, fails when the build output is missing, and with `COCURDEX_DESKTOP_PACKAGED=1` launches the packaged app from `apps/desktop/release` instead. Keep `tests/e2e` free of LLM providers, network, keychain, and UI assertions.

Agent behavior in tests comes from `tests/harness/helpers/llm-stub.ts`, a local OpenAI-compatible server that drives the real Pi adapter: a `script` plan replays text and tool calls (`read`, `write`, `edit`) turn by turn, so runs, tool outcomes, and file changes go through production code. Do not add test-only adapters or test hooks to the daemon.

Shared product data for tests comes from the fixture database: `tests/harness/fixture-db/recipe.ts` declares a synthetic workspace (`tests/harness/fixtures/acme-shop`), sessions with scripted turns, notes, and issues, and `installFixtureDb` builds it through a real daemon and installs it into a userData path. Scenarios opt in with `openScenarioApp(args, { fixtureDb: true })` or `--fixture-db`. Extend the recipe instead of hand-building data in each test. Fixture content must be invented: never copy data from a real `cocurdex.sqlite`, and keep names, emails (`example.invalid` only), paths, and credentials synthetic; `fixture-db.test.ts` scans the built database for home paths, machine identity, emails, and token shapes.

`tests/scenarios` holds app-level e2e scripts that drive the real desktop UI over CDP, for example `node tests/scenarios/pdf-reader.mjs`. By default a scenario launches its own isolated instance (fresh short userData path, free CDP port, its own `electron-vite dev` renderer server), seeds a workspace with its fixtures, runs, prints a JSON report, and stops the instance tree; `COCURDEX_SCENARIO_RENDERER=built` launches the production build from `apps/desktop/out` instead (rebuilt when sources are newer), which is what CI runs, so scenarios must not depend on dev-only hooks such as Vite module imports or `window.__cocurdexDebug`; `--port <cdp port>` attaches to a running app instead, and `--keep` leaves the isolated instance up for debugging (`tests/scenarios/stop-instance.mjs` stops it). `pnpm test:ui` runs every scenario against one shared isolated instance with the fixture database, re-seeding workspaces and reloading the renderer between scenarios; pass scenario names to run a subset and `--isolated` to give each scenario its own instance. Build new scenarios on `tests/scenarios/lib`: call the daemon with `lib/daemon-rpc.mjs`, translate labels with `translate` from `lib/navigate.mjs`, and switch themes with `lib/appearance.mjs`. Reach views through `lib/navigate.mjs` (`showPanelView`, `openNote`, `openNewIssueDialog`, `openSettingsSection`, `openExecutionTree`); when a scenario needs an entry point it lacks, add it there instead of rediscovering it in the script. Locate elements by role and accessible name with `lib/locate.mjs` (CDP accessibility tree), fall back to domain `data-*` attributes such as `data-item-path` for rows without a semantic name, and do not select by CSS classes or DOM structure; when a control has no usable role or name, fix its accessibility in the component. Wait for the expected state instead of sleeping after an action.

Turn every verification you would repeat, and that clears the value bar above, into a deterministic script in the same change, so the next run executes it instead of re-deriving it: UI flows go into a scenario, daemon and CLI behavior into `tests/e2e`, and checks against build output (the bundled `daemon.cjs`, the packaged app) into the `test:desktop` suite, which runs after a build. When a manual check finds a bug, first write the assertion that fails on it, confirm it fails, then fix; commit that assertion only when it clears the value bar. If the bug depends on timing, make the product's ordering deterministic (wait for an explicit ready signal) instead of writing a test that passes by luck. Keep subjective judgments, such as whether a layout looks good, manual, but assert their measurable parts: aspect ratios, overflow, alignment, clearance from window controls, which windows are open.

Startup performance has a baseline. CI fails when the renderer's startup chunks exceed `apps/desktop/startup-budget.json` (`pnpm --filter @cocurdex/desktop check:startup-bundle` after a build) or when desktop code imports `lazy`/`Suspense` from `react`. Raise the budget with `check:startup-bundle --update` only for intended growth, and justify it in the PR. When a change touches startup (entry imports, app shell, bootstrap, main-process `whenReady`), compare `pnpm --filter @cocurdex/desktop perf:startup` on builds before and after; add `--onboarding` for the first-run screen. Reference on Apple Silicon (2026-09-30): returning user FCP about 70–90 ms and LCP about 100 ms.

## Development and UI verification

Start or restart the desktop dev app yourself when verification needs it; do not wait for the user. When a renderer edit does not show up after HMR (for example, new Tailwind classes missing from the served CSS), restart the instance at once instead of waiting or debugging HMR. A change to main, preload, or the bundled daemon needs a restart, since HMR only reloads the renderer: run `pnpm --filter @cocurdex/desktop dev:inspect`, which rebuilds `prepare:cli` and spawns the rebuilt daemon. To restart a running dev app, stop the exact `dev:inspect`/`dev` process tree you found (by PID, never by process name), relaunch it detached with output redirected to a log file that outlives your shell, wait for the CDP port, and tell the user the log path. Restart the user's dev app whenever a change needs it, even while agent runs or other work in it are in progress; the user accepts the interruption, so do not hold back a restart or route around it with an isolated instance.

You may attach to a running desktop app over Chrome DevTools Protocol yourself to debug, without asking first: read the renderer console, evaluate JavaScript, inspect the DOM, measure layout, and take screenshots. Keep the attach disposable: detach when the investigation is done, and restore what you changed (open views, theme, test data).

After finishing a feature or bug fix that changes user-facing behavior, run an end-to-end check yourself and report it; do not hand verification to the user. Drive the real app over CDP — click, type, navigate, open the affected views — or a browser for the web client, covering the main flow, edge cases, and both themes when appearance changes. Look for functional bugs, console errors, failed requests, and performance or memory regressions. Prefer an existing scenario in `tests/scenarios`, extend it, or add one. Report what you exercised, the measurements, the problems found and fixed, and what you could not cover. Skip this only for changes with no runtime surface, such as docs, tooling, or pure refactors already covered by tests.

Several worktrees and agents run e2e at the same time, so every automated check must be safe to run in parallel. Never share the user's dev app, its userData profile (`Cocurdex-dev`), CDP port 9222, or a renderer server from another checkout: the single-instance lock and the daemon socket are scoped to the userData profile, so a shared profile makes the second app exit or connect to another worktree's daemon, and a borrowed renderer URL runs another checkout's code. Each instance gets its own short `COCURDEX_USER_DATA_PATH` under `os.tmpdir()` (the macOS socket path limit is 103 bytes), its own free `COCURDEX_REMOTE_DEBUGGING_PORT`, and its own `electron-vite dev`, which picks a free Vite port; the scenario launcher does all of this. Attach to the user's app only for checks that need its real data, keep them read-only or restore what you changed, and fall back to running a check alone only when it truly cannot be isolated. Run at most 5 concurrent instances, and stop only the process trees you started, by PID. Stop an isolated instance as soon as you are done with it, including one left up with `--keep` or replaced by a restart; before ending a turn, stop every instance you started that is no longer in use.

Prefer measuring over guessing. When a symptom involves rendering, layout, timing, or third-party behavior and a CDP session can answer it, attach and measure before proposing a cause or a fix; state the measurement that settled it. Do not stack hypotheses, batch speculative fixes, or ask the user to re-verify round after round when the running app can be inspected directly.

Final visual and UX acceptance stays with the user. After your end-to-end check, briefly state what changed and which screen to inspect. Diagnose runtime errors, console exceptions, and reproducible functional failures yourself through code, logs, and a CDP session.

## Code structure and imports

- Keep feature-specific components, hooks, utilities, types, and fixtures together. Move shared code outward only as its reuse scope grows; cross-app reuse belongs in `packages`, not imports between apps.
- Give source folders an `index.ts` or `index.tsx` public entry that exports only what consumers need.
- Across features in `apps/desktop/src`, use `@/*`; across packages, use `@cocurdex/*` public entries. Within a feature, use short relative imports.
- Do not bypass boundaries with `packages/*/src/*`, `apps/*/src/*`, deep relative paths, or internal file imports. Add missing public exports instead.
- Avoid long lines and nested ternaries. Use named values, helpers, `if`, or lookup tables for complex branches.
- Before editing a code file over 400 lines, prefer extracting cohesive components, hooks, utilities, or fixtures unless that reduces clarity or expands scope. Markdown files are exempt.
- Desktop-specific rules (barrels, lazy loading, UI components, appearance tokens, React hooks, Fast Refresh) live in `apps/desktop/AGENTS.md`.
- Mobile-specific rules (Expo, native projects, credentials, visual language) live in `apps/mobile/AGENTS.md`.

## Product knowledge and skills

- PRDs, specs, notes, and issues live only in the daemon-owned `cocurdex.sqlite`. Never write them into the workspace or open the database directly; use the `cocurdex` CLI.
- Use namespaced skills: `/cocurdex-note` for notes, PRDs, specs, and links -> `/cocurdex-issue` for issues and their status while you implement them. Parallel teammate agents: `/cocurdex-team`; scripted fan-out to background subagents: `/cocurdex-script-run`; slide decks: `/cocurdex-deck`; app settings: `/cocurdex-settings`; installing and updating agent skills: `/cocurdex-skills`. Open decisions are issues labeled `decision`, settled with the user through `/cocurdex-decide`. Todo and ticket mean issue.
- Manage issues (list, show, create, move, delete, views) through `@cocurdex/cli` using `cocurdex issue ...`. Never invent IDs or manually rewrite status.
- Distribute skills from `packages/product-skills` through Settings > Skills or `cocurdex skills pack install --scope project|global`; do not auto-install. This repository symlinks the product skills named in `PRODUCT_SKILL_NAMES` (`packages/product-skills/src/manifest.ts`) from `.agents/skills` and `.claude/skills` to that source; never commit installed copies.
- Name new skills for developing this repository `cocurdex-<topic>` too. They live as real directories in `.agents/skills`, linked from `.claude/skills`, and stay out of `PRODUCT_SKILL_NAMES`, so they are never distributed.
