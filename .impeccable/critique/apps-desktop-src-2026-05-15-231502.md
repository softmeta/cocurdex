# Cocurdex 桌面应用 Shell 设计评审

## 范围

目标：`apps/desktop/src`，并通过 `http://localhost:5173/` 检查了正在运行的渲染界面。

已检查界面：

- 空状态应用 Shell
- 左侧会话侧边栏
- 中间新建会话输入区
- 右侧编辑器面板空状态
- 设置里的外观页面

限制：

- `context-mode` transport 不可用。
- 本会话只有在用户明确要求代理委派时才允许启动 sub-agent，所以没有做双代理隔离评审。
- 确定性扫描失败：`pnpm exec impeccable detect --json --fast apps/desktop/src` 以 `fetch failed` 结束。
- 因为 detector 包无法解析，没有运行浏览器 overlay 注入。

## 反模式结论

这个界面不像泛化 AI 生成物。产品避开了渐变文字、玻璃卡片、hero metric、重度紫蓝 SaaS 风格和装饰性动效。对开发者工作区来说，整体克制是正确的。

风险在另一端：界面过于安静，导致早期激活层级不足。空 Shell 里，左侧栏、中间输入区、右侧编辑器面板都以接近的音量呈现。资深开发者能推断出模型，但首次用户需要花力气理解路径：选择工作区，启动会话，查看文件，运行工具。

确定性扫描：不可用。命令以 `fetch failed` 失败，所以没有 detector 数量统计或 overlay 结果。

## 整体印象

Cocurdex 看起来像严肃的原生工具，而不是聊天包装器。应用 Shell 的方向是对的。最大机会是把空状态从稀疏画布变成操作型启动界面，在不写营销文案的前提下教会用户多面板模型。

## 做得好的地方

- 多面板框架支撑了产品定位。`AppShellFrame` 让侧边栏、中间区域和编辑器成为并列区域，而不是让聊天占满整个产品。
- 主题 token 覆盖面很广。`theme-tokens.css` 已经分离了 chat、sidebar、editor、welcome 和语义角色。
- 设置页对 pre-release 应用来说质量很高。外观控制具体、可检查，也符合 theme parity 的方向。

## 优先问题

### [P1] 空 Shell 缺少激活层级

问题：默认屏幕把输入区居中，但 “首页”、工作区选择、模型、权限、计划模式、运行时配置、附件和发送都挤在同一个安静控件组里。没有元素明确承担第一步。

证据：`apps/desktop/src/features/sessions/new-session-card.tsx:150` 从工作区选择开始，然后 composer 面板成为主界面。实际 UI 中，即使没有工作区，composer 仍然看起来像主动作。

影响：Cocurdex 的承诺是跨 session、terminal、editor、browser 完成完整 feature loop。当前首屏更像在说“输入聊天”，而不是“启动工作区会话”。

修复：在无工作区状态下，把 “Open Folder” 做成主动作，并把 agent/model 控制移到次级设置行。工作区存在后，再把层级切回 prompt composer。保持密度，但明确状态转变。

建议命令：`impeccable onboard apps/desktop/src/features/sessions/new-session-card.tsx`

### [P1] 设置页仍让应用界面留在可访问性树里

问题：打开设置时，原应用 DOM 仍和设置一起出现在 snapshot 中。部分非活动应用层控件还失去了可访问名称。

证据：`apps/desktop/src/app/layout/app-shell-frame.tsx:85` 用 `aria-hidden` 隐藏 app，而 `SettingsScreen` 在 `apps/desktop/src/app/layout/app-shell-frame.tsx:189` 挂载。浏览器 snapshot 仍显示 app 控件和 settings 控件同时存在。

影响：屏幕阅读器和键盘用户可能遇到活动设置页下面的旧 app 控件。它也削弱心智模型：设置视觉上像独立屏幕，但语义上不够干净。

修复：让 active screen 的所有权更严格。优先只渲染当前 active screen，或者给非活动屏幕加 `inert` 并验证焦点管理。确保非活动树不可到达，非活动层里的无名图标按钮不会暴露。

建议命令：`impeccable harden apps/desktop/src/app/layout/app-shell-frame.tsx`

### [P2] 右侧编辑器面板在空状态下工具栏过于晦涩

问题：编辑器面板图标密度高，但没有工作区或文件时，用户在有意义内容出现前先看到六个工具栏按钮。

证据：`apps/desktop/src/app/layout/right-editor-panel.tsx:197` 渲染编辑器工具栏，包括 202-230 行的多个纯图标按钮。实际空面板显示 editor、browser、git、terminal 选择器，再显示文件控制，最后才是 “No workspace” 和 “No file selected”。

影响：右侧面板应该证明 Cocurdex 不只是聊天。空状态下，它反而用一圈无解释 chrome 包住空内容。

修复：在存在工作区或文件前，隐藏不可用的编辑器工具栏动作，或者把工具栏区域替换为紧凑的 “Open folder” 空状态。保留 view switcher，因为它解释面板范围。

建议命令：`impeccable distill apps/desktop/src/app/layout/right-editor-panel.tsx`

### [P2] 桌面宽度下视觉节奏过于平均

问题：Shell 使用一致的低对比面板，但中间和右侧空状态都落在同一组克制色阶里。右侧面板占走宽度后，composer 仍以固定卡片姿态充当页面锚点。

证据：`apps/desktop/src/app/layout/app-shell-frame.tsx:161` 给中间区域 flex 空间，而 `apps/desktop/src/features/sessions/new-session-card.tsx:123` 固定 composer 最大宽度。右侧面板打开后，composer 仍像页面主锚点。

影响：多面板界面需要清楚的 pane priority。所有区域都同样安静，会让用户扫描而不是行动。

修复：为三种状态定义响应式层级：无工作区、有工作区但无会话、活动会话。三面板模式下，减少 composer 装饰，提高 workspace/session 上下文权重，并让右侧空状态明显处于从属位置。

建议命令：`impeccable layout apps/desktop/src/app/layout`

### [P3] 原始 hex token 和 OKLCH 方向冲突

问题：主题 token 大量使用 hex 和 rgba。

证据：`apps/desktop/src/styles/theme-tokens.css:4` 以后。

影响：当前视觉结果可控，但设计系统方向要求 OKLCH 和带色相中性色。hex 会让后续主题变体的感知调整更困难。

修复：做一次聚焦 pass，把设计层面的颜色 token 转成 OKLCH。只有生成值或库强依赖的值才保留原格式。

建议命令：`impeccable colorize apps/desktop/src/styles/theme-tokens.css`

## Persona 风险

高阶用户：键盘能力很强，但空状态没有充分显示 session/workspace 状态。用户完成设置后能跑得快，但初始状态藏住了产品的多 agent 优势。

首次使用的开发者：“Home”、“Codex”、“Default permission”、“Plan mode” 和 “Default runtime config” 在应用解释为什么要打开工作区之前就出现了。风险：用户把 Cocurdex 当成更好看的聊天框。

键盘和辅助技术用户：设置页视觉上替换了应用，但浏览器 snapshot 仍能检测到非活动 app 控件。风险：焦点顺序和阅读顺序变混乱。

## 次要观察

- 侧边栏账号条很完整，但源码里可见的硬编码 `richardwong` 在更广泛测试前应该替换掉。
- 设置页的层级比空应用 Shell 更好。可以把它作为内部质量基准。
- 工具栏图标尺寸一致，这是好的。问题在命名、可用性和状态，不在图标执行本身。
- 右侧面板开关激活时很清楚，但面板打开后，它的位置会和 panel view switcher 竞争。

## 需要考虑的问题

- 无工作区屏幕最应该让用户无法忽视的动作是什么？
- “Home” 应该是一个真正的操作界面，还是只是无工作区时的 fallback 标签？
- 哪些控件应该在工作区存在前消失？
- 设置应该是 route 级替换，而不是 overlay 屏幕吗？

## 建议的下一轮

先跑 `impeccable onboard apps/desktop/src/features/sessions/new-session-card.tsx`。激活层级是收益最高的修复。然后跑 `impeccable harden apps/desktop/src/app/layout/app-shell-frame.tsx`，解决语义 screen ownership。
