# Cocurdex mobile

Rules for `apps/mobile`, in addition to the repository root `AGENTS.md`. iOS and Android are equally supported; design, implement, and verify every change for both.

## Expo and native projects

- The app is an Expo app on the latest stable SDK. Add or upgrade a package with `pnpm exec expo install <package>`, which picks the version the SDK supports, and check the set with `pnpm exec expo install --check`. `expo install` writes ranges at releases too new for pnpm's minimum release age and then adds `minimumReleaseAgeExclude` entries: revert those entries, relax the range to `~<major>.<minor>.0`, and reinstall from the last clean lockfile. Expo SDK releases rename and remove APIs: read the docs for the SDK major in `package.json` before using an Expo or React Native API.
- `ios/` and `android/` are generated by `expo prebuild` and ignored by Git. Configure native behavior only in `app.json` and config plugins; never edit the generated projects. `app.config.js` sets the iOS build number and Android `versionCode` from `COCURDEX_MOBILE_BUILD_NUMBER`, falling back to the Git commit count; set it explicitly for TestFlight and Play uploads, since a shallow CI checkout counts one commit.
- Routes live in `src/app` (Expo Router). Keep app code outside `src/app` in feature folders with an `index.ts` public entry, imported through `@/`.
- Share product contracts through the main entries of `@cocurdex/shared`, `@cocurdex/rpc`, and `@cocurdex/client-runtime`. Those entries must stay free of Node built-ins; never import `@cocurdex/shared/node` or daemon packages.
- Store credentials and paired hosts only through `secureStorage` from `@/storage`: the system keychain with this-device-only access, split into chunks below the 2 KB value limit some iOS releases enforce. Never put tokens in AsyncStorage, files, or logs.
- The app talks to daemons over plain HTTP and WebSocket on the local network: iOS allows it through `NSAllowsLocalNetworking`, Android through `usesCleartextTraffic`. Remote access goes through Tailscale. Do not add other transport exceptions.
- Take colors from `useThemeColors()` and spacing from `@/theme`. Colors are generated from the desktop's `theme-preset.css` and `theme-tokens.css` into `src/theme/colors.generated.json` (`pnpm --filter @cocurdex/mobile generate:theme-colors`), so both apps share one palette; change a color in the desktop CSS, never in the JSON. Add a metric to `src/theme/metrics.ts` only when the visual language below defines it.
- Product state the daemon pushes (sessions, attention, transcripts) lives in per-host stores built on `useSyncExternalStore` and the host connection's events. Request/response reads (agent lists, models, defaults, notes, issues) use `swr` like the desktop: keys start with the RPC method and host id followed by every parameter that changes the result, local daemon reads pass `{ dedupingInterval: 0 }`, and a feature keeps its keys and hooks in one `*-queries.ts` module. Revisiting a screen renders the cached result while it revalidates.
- Never load code from the network at runtime. Mermaid diagrams render in one shared offline WebView whose runtime, `src/markdown/mermaid-runtime.generated.ts`, is bundled from the `mermaid` devDependency by `generate:mermaid-runtime`; rerun it after changing the dependency (CI checks it with `check:mermaid-runtime`).
- Move large or binary data by streaming over HTTP (attachments use `/attachments/*`), never as base64 in RPC payloads.
- Every user-visible string goes through `t()` from `react-i18next`, in i18next JSON under `src/locales/<locale>/<namespace>.json` with the same conventions as the desktop, so one localization pipeline serves both apps. Use literal keys (no template strings), so `i18n:extract` sees them. After adding keys, run `pnpm --filter @cocurdex/mobile i18n:extract`, fill en-US and zh-CN, then `i18n:types`, `i18n:lint`, and `pnpm exec biome check --write apps/mobile/src/locales apps/mobile/src/i18n`. The locale comes from the system (`expo-localization`, per-app language included) through `matchSupportedLocale` from `@cocurdex/shared`. Translate native strings such as permission prompts in `native-locales/`.

## Verification

1. `pnpm --filter @cocurdex/mobile typecheck`.
2. `pnpm exec expo export --platform ios` and `--platform android` from `apps/mobile` to prove both bundles resolve, with `--output-dir` pointing at a temporary directory.
3. For user-facing changes, iterate on a debug build on a simulator or emulator with `pnpm --filter @cocurdex/mobile ios` or `android` and check light and dark: install it once, keep Metro running with `CI=false` (Metro started without a TTY runs in CI mode and serves no edits), and verify each JS change through Fast Refresh and screenshots (`xcrun simctl io booted screenshot`, `adb exec-out screencap -p`). Rebuild only after native changes (dependencies, `app.json`, config plugins). In dark, check every sheet, menu, and floating control against what it covers: its edge must read against the page behind it, and its rows against the sheet; when unsure, sample both colors from the screenshot instead of judging by eye. `/cocurdex-mobile-verify` covers the isolated daemon (`preview --dev`), deep-link pairing, and driving the app with `agent-device`.
4. CI runs the Maestro flows on both platforms for every PR and uploads their screenshots; push a finished batch of changes and let CI run them instead of running the full suite locally. Run them locally only when you change a flow or its selectors, or to reproduce a CI failure its artifacts do not explain: `pnpm --filter @cocurdex/mobile-e2e flows -- --platform ios|android [--build]`. The runner builds the bundled daemon and a Release app with `--build`, starts its own simulator or read-only emulator and an isolated bundled daemon, runs every flow in light with en-US and in dark with zh-CN, and removes what it started. Each flow pairs on its own; CI runs each Android flow on its own runner and the iOS flows two per runner, since parallel macOS runners slow each other's simulators; pass `--flow pairing|transcript|compose|library` to run a subset. Flows read visible labels from `src/locales` through environment variables instead of hardcoding English. It needs the Maestro CLI and Java 17+.

Unit tests for mobile modules live in `tests/unit/mobile` and import them through `@cocurdex/mobile/internal/<path>`. UI flows live in `tests/mobile/flows` as Maestro YAML: locate elements by visible text, accessibility label, or `testID`, and add a flow or extend one for every user-facing change.

## Visual language

The app looks and behaves like a native iOS app on iPhone and a native Material 3 app on Android, not like the desktop UI in a phone frame. The platform draws controls, navigation, and overlays; Cocurdex supplies content, its palette, and the meaning of each color. Every screen covers light and dark.

- Build every screen against its mockup in the mobile design canvas (https://claude.ai/artifact/4DL1AGnYM3X6BhSQ8PSTvw, one board per screen in light and dark). Read the board before implementing or changing a screen, and match its layout, content, hierarchy, spacing, and colors as closely as the platform allows. Deviate only where a native component or a platform limit forces it (for example a native tab bar, header, search field, or sheet that cannot be drawn as the board shows), and list each deviation with its reason in the PR. When the rules below and a board disagree, follow the rules and flag the board for revision instead of copying it.

- When a native component or platform convention forces the platforms to differ, follow each platform's own guidelines and conventions (Apple Human Interface Guidelines on iOS, Material 3 on Android) rather than inventing a shared compromise. The desktop's UI and interactions are reference only: carry over the product's content and meaning, but arrange and drive each screen the way a native mobile app does, with mobile patterns such as sheets, pushed pages, swipe actions, and pull to refresh instead of desktop menus, hover, or dense toolbars.
- iOS and Android share one UI and UX: the same screens, layout, navigation structure, toolbar placement, wording, and flows. Each platform renders them with its native controls, but nothing is arranged or behaves differently per platform. Write one component; add a `.ios.tsx` or `.android.tsx` file only when a platform API forces it, keep its result identical to the other platform, and run the same Maestro flows on both. Give a platform file the same extension as its default file (`x.tsx` beside `x.android.tsx`): Metro tries every platform suffix per extension, so `x.ts` wins over `x.android.tsx` and Android silently runs the default.
- Navigation starts from Expo Router's native stack and native tabs, with the platform's large titles, back gestures, and transitions. The goal is the best result on screen, not native components for their own sake: draw a header or tab bar in React Native only when the native one cannot match the board or cannot change in the same frame as the content, and keep the platform's sizes, gestures, and transitions when you do. Both platforms draw the tab bar as one floating icon capsule in React Native (`src/tabs`, Expo Router headless tabs): Material's bottom navigation is docked, and iOS before 26 docks its tab bar with labels and a divider. Every scrolling surface inside a tab adds `useTabBarInset()` to its bottom padding so content scrolls under the capsule and its last row stays reachable; `Form` does this already.
- A screen renders through one pipeline. A SwiftUI or Jetpack Compose host (`@expo/ui`) commits a frame or more after the React Native views around it, so a screen that mixes them shows a theme or state change in two steps. Forms, settings rows, and anything sharing a screen with React Native content are React Native views from `@/ui`; `@expo/ui` serves self-contained overlays such as dialogs; sheets are `formSheet` routes. Prefer a mature open-source component over a hand-written one when it renders both platforms' own look; otherwise write a thin component in `@/ui` that keeps each platform's sizes, shapes, and touch feedback.
- Type uses the system font and the platform's text styles, and scales with the user's text size setting. Do not fix font sizes that ignore Dynamic Type or Android font scale.
- Brand teal is the platform tint (iOS `tint`, Android `seedColor`) and otherwise a small mark only: unread dots, selected checks, links, the running mark, done status. Never fill a large surface with it or with a status color.
- Each screen shows at most three hues; neutrals do not count. Every hue means one thing app-wide: teal is active or healthy (running, unread, done, online), blue is waiting for the user, red is failure or a destructive action, and orange is only an issue's in-progress status. Content colors (diff lines, syntax highlighting, user-chosen labels) appear only in content views such as a diff; summaries elsewhere, like `+36 −2` in a transcript, stay neutral.
- Content lists (sessions, issues, notes, archived sessions, computers) are plain full-width lists without row separators, as in Linear: rows are separated by 12pt vertical padding, groups by `ListSectionHeader` (muted title, optional count and collapse chevron), and empty or failed states by `ListNotice` (muted icon, title, description, optional action), all drawn in React Native and virtualized with `FlatList` or `SectionList`. Settings and forms use `Form`, `FormSection`, `FormRow`, `FieldSection`, `FormTextField`, `FormText`, and `FormNote` from `@/ui`, which draw the platform's grouped form (inset grouped on iOS, Material segmented groups on Android) from one file; platform metrics live in `form-metrics.ts`. Pass strings as row content so the row applies the platform's text style. Set `adjustsForKeyboard` only on a `Form` that holds text fields: iOS applies keyboard insets to every scroll view that asks for them, including those on screens underneath, and leaves a short screen scrolled out of place. Keep a bordered surface only when the object itself is a card: a kanban card or a slide thumbnail.
- A form sheet puts its primary action in the sheet's toolbar through `SheetAction` from `@/ui`, a tonal circle with a check whose accessibility label names the action and that fades while disabled (iOS draws a native bar button; Android hosts a React Native `CircleButton` in `Stack.Toolbar.View`), and closes through `CloseButton`. A sheet whose changes apply at once (display options, pickers) has no confirm action, only `CloseButton`; never give a header a filled, high-contrast button. Android's `formSheet` is a Material bottom sheet that draws no root-stack header, so a sheet with its own nested `Stack` (display options, filters, labels, session config) is a `formSheet` on both platforms, while a route that relies on the root stack's header (pairing) is a `modal` on Android (Material's full-screen dialog: close, title, primary action in the top bar) with its validation message in the section footer. Blur the focused field and await `keyboardHidden()` from `@/ui` before a sheet with a focused field dismisses.
- Aim for the best result on screen, with Linear's mobile app as the reference for feel: content edge to edge on a near-black or white page, a few surfaces separated by brightness rather than borders, regular-weight type, muted grays, and controls that float over content as capsules and circles. Platform conventions decide behavior (gestures, back, keyboard, accessibility); they do not cap the visual result.
- Actions float. A list screen's title, search, and actions come from `ListScreenHeader` in `@/ui` (a React Native header on both platforms: a bold title with search and the actions in one floating capsule on the same row, no divider; search expands into a field with Cancel); a sheet or modal closes through `CloseButton` and confirms through `SheetAction`, a tonal circle. The tab bar is a floating capsule.
- Every stacked screen has an immersive header: the page background, no divider, a small centered title, and round buttons. Stacks take `useHeaderOptions()` (or `useSheetStackOptions()` inside a sheet) from `@/ui`, which on Android replaces Material's back arrow with a tonal circle; iOS keeps its native back button (a glass circle on iOS 26). Put header actions in `HeaderButtons` from `@/ui`, never in `Stack.Toolbar.Button` directly, so Android draws them as the same tonal circles instead of Material icon buttons.
- Detail screens open for reading. A note shows read-only until the header pencil (`HeaderButtons`) switches it to editing, and a new note starts in edit mode. An issue's properties (status, priority, workspace, labels) change in place from their rows, saved at once without an edit mode; its title and description change in an edit modal with `SheetAction`. Single choices open as bottom sheets; multi-select (labels) opens a form sheet whose rows toggle and save immediately.
- Layers separate by brightness, most of all in dark, where a scrim barely dims a near-black page. Anything raised above the page (bottom sheets, anchored menus, floating capsules) sits on the `popover` surface, and rows inside it step up once more (`muted` in dark), so the sheet stands apart from the page behind it and its rows stand apart from the sheet. Wrap a sheet's nested `Stack` in `SheetSurface` from `@/theme` so `useGroupedColors()` and `FormCell` pick the sheet palette; never give a sheet the page background.
- Controls floating over scrolling content (the transcript's jump button) use a flat, opaque fill that contrasts with both the page and code panels in each theme; never a drop shadow.
- A short menu of actions or options (up to about six, no search) opens anchored at the control or row that opened it (`useAnchoredMenu` from `@/ui`, opened with `menuAnchor(event)` from a press or long press, or `measureAnchor` from an accessibility action): large corner radius on the `popover` color, rows with an optional leading icon and trailing check, separators between groups. Long lists, searchable choices, and pickers (agents, models, workspaces) open through `useOptionSheet` from `@/ui`: every bottom sheet in the app is one `formSheet` route with the same chrome (grabber, `CloseButton`, centered title, grouped rows), so never present a sheet through `@expo/ui` `BottomSheet`. From a page it opens the root `options` sheet; inside a sheet's nested `Stack`, provide `OptionSheetRouteProvider` and an `options/[id]` screen so the choice drills in within that sheet instead of stacking a second sheet. Android draws no native grabber, so `SheetSurface` draws one there. A short destructive confirmation may use the platform alert. Do not build other custom modals.
- Session states that wait for the user (permission, question, plan approval, failed run) dock at the bottom, above or in place of the composer, without a scrim, so the transcript stays scrollable for context; this matches the desktop's docked cards. Once resolved, they remain in the transcript as history.
- Spacing sits on a 4pt grid with one 16px side margin for custom content; native lists and forms keep their own insets. Custom tappable content keeps a 44pt (iOS) / 48dp (Android) hit area.
- In two-line rows, leading icons and trailing status align with the title line; only avatar-sized tiles (about 36px) center on the whole row. A list's trailing column holds the same kind of content in every row, for example time on the title line and one fixed status slot on the second line.
- Layouts are fluid from 320px to 430px wide; never fix a pixel width on a container, column, or control. Mockups are drawn once at 390×844, with 320×568 boards for screens that crowd. When side-by-side actions do not fit, wrap them and give the primary action its own line; do not shrink type or truncate a button label. Secondary row details (model, branch, counts) drop to the second line instead of competing with the title. Board columns are the screen width minus 90px so the next column always peeks in, and message bubbles are at most 85% wide.
- Wider screens (tablet) change navigation, not components: they may switch to split views at the shell level, while components never branch on screen width. Tablet layouts need their own mockups before implementation.
